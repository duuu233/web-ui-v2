## 1. 外部数据源：只用老后台两张表

本服务**不重复建模产品与设备归属**，全部从老后台取。

### 1.1 产品列表

| 字段 | 我们是否使用 | 用途 |
|---|---|---|
| 产品 ID | ✅ **必用** | 槽位表主键之一；设备 ↔ 产品的关联键 |
| 产品名称 | ✅ **必用** | 后台展示（如「7.09 全彩电子纸相框」） |
| 版本类型（wifi / 蓝牙） | ✅ **必用** | **过滤：只处理 wifi**；蓝牙版不走 MQTT，没有内置图下发 |
| **渲染模式（esp32 / fpga16）** | ✅ **必用** | **和「屏幕方向」一起决定 SDK screenType**（见 §7.1 对照表）。取值与本服务 `/api/device/play` 的 `renderMode` **同名同值**，可直接用 |
| 形状类型（圆 / 方） | ⚠️ 暂不用 | 目前没有圆屏产品；将来若出现圆屏，需要做遮罩 |
| **屏幕方向（横屏 / 竖屏）** | ✅ **必用** | **决定渲染前要不要把画布转 90°**：横屏 → 转（等价现有 `type=1`）；同时参与 screenType 选择 |
| **尺寸(cm)**（值形如 `1200*1600`） | ✅ **必用** | **画布像素宽高**。字段名叫「尺寸(cm)」，但值**已确认为像素 `1200*1600`**（三款产品一致，不分横竖）。**横屏产品也配 1200\*1600，由服务端旋转** |
| 尺寸型号（如「13.3寸」） | ⚠️ 只展示 | 纯文字，无逻辑用途 |
| 广播 ID | ❌ 不用 | 配网用，与内置图无关 |
| 横向旋转度数 | ❌ 不用 | **前端上传图片时已应用**（内容方向），本服务收到的图内容已正 |
| 竖向旋转度数 | ❌ 不用 | 同上 |

### 1.2 产品设备（= 配网白名单）

| 字段 | 我们是否使用 | 用途 |
|---|---|---|
| 所属产品 ID | ✅ **必用** | `deviceNo → productId → 尺寸/方向/渲染模式` |
| 设备 ID | ✅ **必用** | 即 `deviceNo`（12 位大写无冒号） |
| **禁用 / 启用** | ✅ **必用** | **禁用设备：不参与推送、不计入「未推送」统计** |

## 2. 两种旋转的分工（最容易搞混，必须先说清）

| 旋转 | 谁做 | 作用 | 我们是否参与 |
|---|---|---|---|
| 横向 / 竖向旋转度数 | **前端上传图片时** | 让**图片内容**方向对。例：竖向旋转度数 180 → 上传的图是倒的 | ❌ 不参与，收到的图内容已经是对的 |
| 屏幕方向（横 / 竖） | **本服务渲染前** | 让**画布**从竖变横。横屏产品 = 竖图画布转 **顺时针 90°** | ✅ 必做 |

> 现有代码里这个"画布旋转"就是 `type=1`：[BoltStarBinConverter.java:97](../src/main/java/com/boltstar/iot/content/BoltStarBinConverter.java#L97) →
> [prepareImage()](../src/main/java/com/boltstar/iot/content/BoltStarBinConverter.java#L146-L155) 做像素级顺时针 90° 重排。
> 接内置图时：**产品「屏幕方向=横屏」→ 传 `type=1`**。

## 3. 数据模型

> ✅ **已迁移 MySQL（2026-11-10）**：4 张表已建、`xt_iot` 已授权（DML + INDEX/ALTER）。
> 槽位 / 任务 / 明细 / 设备状态走 `BoltStarIntimgRepository`；Redis 只保留**设备锁**
> （`xt:boltstar:dev:intimg:lock:*` + 锁索引）、**清单缓存**（`xt:boltstar:dev:intimg:manifest:*`）
> 和**任务号序列**（`xt:boltstar:dev:intimg:seq:*`）。
> 任务计数不落库，查询时按明细聚合，避免计数器漂移；任务表只维护 `status` 与 `finished_at`。
> DDL 与授权语句见 [sql/iot_intimg.sql](sql/iot_intimg.sql)，含已建表补索引的 ALTER。

### 3.1 `iot_intimg_slot` — 槽位表（产品 × 槽位）

| 字段 | 来源 / 说明 |
|---|---|
| `id` | PK |
| `product_id` | 老后台产品 ID |
| `slot_key` | 6 个 key 之一（见 §4） |
| `bin_url` / `bin_size` / `crc16` | 渲染产物 |
| `canvas_width` / `canvas_height` | **渲染时从产品「尺寸(cm)」解析后冗余存一份** |
| `render_mode` | 冗余：`esp32` / `fpga16` |
| `orientation` | 冗余：`横屏` / `竖屏` |
| `source_url` | 运营上传的原图（留档） |
| `version` | 每次替换 +1 |
| `updated_by` / `updated_at` | |

唯一键 `(product_id, slot_key)`。**行数 = 产品数 × 6**（当前 3 款 = 18 行）。

### 3.2 `iot_intimg_push_task` — 推送任务表

`task_no`、`product_id`、`target_slots`（运营目标槽位 JSON）、**`versions_json`（实际下发前缀的版本快照）**、
`total/success/failed/pending/canceled`（计数冗余）、`status`、时间、操作人。

> **前缀下发**：新任务 `slot_key` 留空；`versions_json` 只存实际下发的槽位（FACTORY 到最高目标）。
> 历史逐槽位任务的 `slot_key` 仍有值，前端按可空兼容。

### 3.3 `iot_intimg_push_item` — 推送明细（每台设备一行）

`task_id`、`device_no`、`status`、`attempts`、`error_code`、`updated_at`。
索引：`(task_id, status)`、`(device_no, status)`。

### 3.4 `iot_intimg_device_state` — 设备 × 槽位成功记录

`device_no`、`slot_key`、`product_id`、`version`、`updated_at`。唯一键 `(device_no, slot_key)`。

**用途**：判断「已推送当前版本 / 落后 / 未推送」，见 §6.2。

## 6. 判定规则

### 6.1 哪些设备参与推送

```
可推送设备 = 老后台「产品设备」中 所属产品ID = 当前产品
             AND 启用状态 = 启用
             AND 已激活（我们库里有该 deviceNo 的 iot_device 记录）
```

**已激活**的判定：`iot_device` 表里有该设备（webhook / 心跳 / 启动同步三条路都会 upsert，见 §9）。

### 6.2 「未推送 / 落后 / 最新」（6 槽聚合）

单槽位仍按版本号比较，但**页面展示的是设备整体状态**：

```
单槽位：未推送 = state.version IS NULL
        落后   = state.version < 当前 slot.version
        最新   = state.version = 当前 slot.version

设备整体：LATEST     = 6 个槽位全部「最新」
          OUTDATED   = 至少一个槽位「落后」
          NOT_PUSHED = 6 个槽位全部「未推送」
```

> 同时返回 `pushedSlots`（0~6，已最新数）与 `outdatedSlots`，供前端展示「已推送 x/6」。
> 不看"上次任务时间"，只看状态表。**新入网设备天然没有状态行 → 自动算未推送。**
> 库存机（已登记未激活）不在「可推送设备」里，因此不计入统计。

### 6.3 明细状态

| status | 含义 |
|---|---|
| `PENDING` | 待推送 / 待补发 |
| `SENT` | 已下发，未拿到结果 |
| `SUCCESS` | **设备回报执行成功（唯一成功判据）** |
| `FAILED` | 下发失败 / 设备回报失败 |
| `EXPIRED` | 超期未补 / 槽位版本已更新 |
| `SKIPPED_BUSY` | 设备正在别的任务中 |
| `CANCELED` | 运营手动取消 |

> **设备回执现状**：`down_int_img_ack` 只观测到 `106`（指令接收成功），从未收到 `113`。
> 因此 `SENT` 就是当前能拿到的最好结果；任务完成口径改为「没有 `PENDING` 即 `DONE`」，
> 迟到的 `113` 仍会把明细修正为 `SUCCESS`（msgid 映射保留 7 天）。

## 7. 关键取值链路（这一节是开发重点）

### 7.1 上传图片时

**先看这张对照表**——两个老后台字段共同决定 SDK 的 screenType，配错就会生成另一款机型的 bin。
（下表「老后台取值」已于 2026-11-10 确认：7.09 / 13.3 都是**竖屏**，10.1 是**横屏**）

| 产品 | `渲染模式` | `屏幕方向` | 传给渲染器 | 现有代码实际命中的 screenType | 产物字节 |
|---|---|---|---|---|---|
| 7.09 | `esp32` | 竖屏 | `type=0` + `renderMode=esp32` | `SCREEN_7_09_E6(33)` | 960,004 |
| 13.3 | `esp32` | **竖屏** | `type=0` + `renderMode=esp32` | **`SCREEN_7_09_E6(33)`**（不是 31） | 960,004 |
| 10.1 | `fpga16` | 横屏 | `type=1` + `renderMode=fpga16` | `SCREEN_10_E6_FPGA(150)` | 3,840,000 |

> 依据：[BoltStarBinConverter.resolveScreenType()](../src/main/java/com/boltstar/iot/content/BoltStarBinConverter.java#L171-L189) —
> `esp32` 按 `type` 分 33（竖）/31（横），`fpga16` 一律 150（不看 `type`），但 `type` 仍决定**是否旋转**（[convert():97](../src/main/java/com/boltstar/iot/content/BoltStarBinConverter.java#L97)）。
>
> **13.3 的机型等价（已实机验证，无需处理）**：13.3 配竖屏，因此走的是 7.09 的 `SCREEN_7_09_E6(33)`，
> 代码里 `SCREEN_13_3_E6(31)` 分支在内置图路径上不会用到。用户已于 2026-11-10 确认 13.3 现有配置在实机上全部验证通过，
> 且同一张 1200×1600 输入下 31 与 33 产物逐字节相同（`placeholder_133.bin` 与 `placeholder_709.bin` md5 均为 `c9ef7f12…`）。
> 仅在代码里留一行注释说明该依赖即可，不需要额外适配。

| 步骤 | 取什么 | 从哪取 | 怎么用 |
|---|---|---|---|
| ① 定产品 | `product_id` | 页面已选 | 定位槽位行 |
| ② 取渲染参数 | `尺寸(cm)` → `1200*1600` | **老后台「产品列表」** | 解析成 `canvas_width/canvas_height`，**校验上传图必须等于该尺寸** |
| | `屏幕方向` | 同上 | `横屏` → 渲染前转顺时针 90°（`type=1`）；`竖屏` → 不转 |
| | `渲染模式` | 同上 | 按上表映射 screenType |
| ③ 渲染 | 源图 + 上两步参数 | 本地 | 调 SDK 生成 bin；**格式以固件提供的 `img_set.bin` 为准**（见 §7.1.1） |
| ④ 存 | bin | OSS | 写 `bin_url/bin_size/crc16`，`version+1` |

> **注意**：`横向旋转度数 / 竖向旋转度数` **不在这里用** —— 它们是前端上传前就应用到图片上的，
> 我们收到的图内容方向已经正确。

**取值校验（任何一个不合法都拒绝，不猜、不兜底）**

| 字段 | 非法情况 | 处理 |
|---|---|---|
| `尺寸(cm)` | 为空 / 不是 `整数*整数` / 宽高任一 ≤ 0 | 拒绝上传，提示「产品尺寸未配置正确，请先联系管理员」 |
| `屏幕方向` | 不是「横屏 / 竖屏」 | 拒绝，不默认按竖屏处理 |
| `渲染模式` | 不是 `esp32` / `fpga16` | 拒绝（与现有 `resolveScreenType` 的 `4000` 一致） |
| 上传源图 | 宽高 ≠ `尺寸(cm)` | 拒绝，提示实际尺寸与产品要求 |

> 理由：内置图是**覆盖设备出厂 UI** 的高风险操作，任何"默认值兜底"都可能把错误尺寸/错误机型的图推给整批设备。

### 7.1.1 内置图 bin 格式（以固件给的 `img_set.bin` 为准）

| 项 | 规则 |
|---|---|
| esp32（7.09 / 13.3） | **960,004 字节** = 4 字节头（`0x04B0`=1200、`0x0640`=1600，大端）+ 1200×1600 的 4bpp 数据（600 字节/行 × 1600 行） |
| CRC | **CRC16/CCITT-FALSE，覆盖整个文件（含 4 字节头）** |
| 参考样本 | `docs/默认图/img_set.bin`：960,004 字节、CRC **58602**、md5 `11ae430cce9e148f8ec11d66e65d9a6e` |
| fpga16（10.1） | `宽 × 高 × 2`（3,840,000），不走上面的 esp32 格式 |

> **实现口径**：后续渲染、尺寸校验、清单 CRC 全部以 `img_set.bin` 这份固件样本为唯一参考，逐字节对齐；
> 2026-11-12 实测 FACTORY 指向原始 `img_set.bin` 时设备在 443 上成功下载 200 / 960,004（是否有可见变化待用户确认）。

### 7.2 设备列表 / 选设备时

| 取什么 | 从哪取 | 怎么用 |
|---|---|---|
| 该产品下的设备 ID 列表 | **老后台「产品设备」**（按 `所属产品ID` 过滤） | 作为候选设备全集 |
| 启用 / 禁用 | 同上 | **禁用设备直接排除** |
| 设备是否已激活 | 本服务 `iot_device` 表 | 未激活的排除（还没配网，推不了） |
| 每台设备的槽位版本状态 | 本服务 `iot_intimg_device_state` | 显示 `最新 / 落后 / 未推送`，并支持筛选 |
| 设备是否在推送中 | 本服务 Redis 锁 | 置灰不可选 |

### 7.3 推送时

| 取什么 | 从哪取 | 怎么用 |
|---|---|---|
| bin 地址 / CRC / w / h | `iot_intimg_slot` | 拼 `down_int_img` 清单 |
| 设备下载用的 host/port | 本服务 `BoltStarDownloadRouter`（按设备 IP 选区域） | 写进 MQTT 指令 |
| 设备在线状态 | 本服务 Redis 在线标记 | 离线 → `PENDING` 等补发 |

### 7.4 谁调老接口（分工已定）

| 数据 | 谁调 | 说明 |
|---|---|---|
| 产品下拉（名称 / 尺寸型号 / 方向 / 渲染模式） | **前端直接复用老后台「产品列表」** | 前端本来就在同一个管理后台里，不经过我们；我们只在接口里接收 `productId` |
| 某产品的设备全集（含未激活库存机、禁用状态） | **本服务服务端调老后台「产品设备」** | 状态页要按「版本状态 + 在线 + 分页」组合查询，设备列表必须先到我们这边才能 JOIN，不能靠前端传大数组 |
| 单设备 → 产品 | **不单独调** | 建任务时按产品一次性取，任务内不再回查 |

> 前置依赖（未确认，§10.1-E）：老后台需提供「按产品 ID 查询设备」的**服务端调用方式**（URL + 鉴权）。
> 若老服务只给前端 token、不允许服务端互调，退化为：前端调老接口取设备分页 → 把当前页设备号传给我们；**此时「全选当前筛选结果」会退化成"全选当前页"**，需要在产品上确认可接受。

### 7.5 老接口调用频率要求（对老服务提的要求）

| 场景 | 频率 | 要求 |
|---|---|---|
| 产品列表 | 前端打开页面时 | 可全量拉取后本地缓存（建议 5 分钟） |
| 产品设备（按产品） | 我们打开设备状态页、建任务时 | **单产品设备量可能上万，必须支持分页查询**，不能一次全量 |
| 单设备查产品 | 推送时逐台 | ❌ **不要逐台调**——建任务时按产品一次性取全量设备列表，任务内不再回查 |

## 8. 异步推送与设备互斥

| 要点 | 说明 |
|---|---|
| 异步 | 接口只建任务 + 入队，立即返回 `task_no`；运营可关页面 |
| 串行 | 任务内按设备串行、按批限速（实测设备会丢弃并发推送） |
| 设备锁 | Redis `xt:boltstar:dev:intimg:lock:{deviceNo}`，`SET NX`；**离线待补发**持有 7 天，**已下发**后 2 分钟由补发扫描释放（不判失败） |
| 释放 | `SUCCESS`/`FAILED`/`EXPIRED`/`CANCELED` 时释放 |
| 补发收敛 | ① 7 天窗口 ② 槽位版本变更即作废 ③ 设备互斥保证同设备只有一条未完成明细 |
| 手动取消 | 任务详情可单台/批量取消并释放锁；设备页可强制释放脏锁 |

## 9. 「已激活」为什么可靠（不用额外设计）

设备连的是 EMQX，本服务重启不影响设备建连。恢复有三条路：

1. **webhook** `client.connected` → upsert `iot_device`
2. **心跳**（每 600s）→ `ensureRegistered()` upsert
3. **启动同步** → 从 EMQX 拉在线列表 → `restoreOnline()` → `markOnlineAndTouch()`（`INSERT ... ON DUPLICATE KEY UPDATE`，能建行）

> 唯一副作用：服务重启期间 App 轮询 `/api/device/online` 会 502，**用户可能误以为配网失败而重配一次**——体验问题，不是数据问题。

## 11. 已知的坑（来自实测）

1. 设备**串行**处理：上一张没下完再推会被忽略 → 任务内必须串行。
2. 设备**按需下载**：不在对应页面时只拉清单、不拉 bin → 推送后不能断言"已生效"。
3. **复位后设备离线**：出厂页只能在离线状态看到，此时推不了。
4. **覆盖不可逆**：没有原厂 bin 备份，覆盖后只能重新上传。
5. **反代链路会截断**：实测 960,004 只传了 514,942 → 需要完整性校验 + 重试。
6. **服务重启期间 App 误判配网失败**（§9）。

## 12. FACTORY 连续前缀下发（2026-11-13 已实施）

> 固件规则：下发清单必须是「从 FACTORY 开始的连续前缀」。
> 只更新 FACTORY → 清单只有 FACTORY；更新 NO_WIFI → 清单必须含 FACTORY、SET、NO_WIFI。
> 中间缺一个槽位，后面的都不能推。

| # | 位置 | 实现 |
|---|---|---|
| 1 | `POST /admin/intimg/tasks` | 入参 `slotKeys`（目标槽位，多选）；服务端自动补齐 FACTORY 起的前缀 |
| 2 | 前缀校验 | 从 FACTORY 起遍历 READY 槽位得到「可更新上限」；目标超过上限返回 `4000`，消息指明缺哪个槽位 |
| 3 | `iot_intimg_push_task` | 新增 `target_slots`（运营目标）；`versions_json` 只存实际下发前缀的版本快照 |
| 4 | 清单生成 | 按任务快照生成，只含前缀槽位；执行期间槽位版本变化 → 明细 `SLOT_CHANGED`，提示重新推送 |
| 5 | 回执写状态 | 只把本次清单内的槽位写入 `iot_intimg_device_state` |
| 6 | `GET /admin/intimg/devices` | 去掉 `slotKey`；返回设备整体状态 + `slots` 6 槽明细 + `pushedSlots/outdatedSlots` |
| 7 | 任务行 | 返回 `targetSlots`、`slotVersions`、`slotVersionText`；历史任务 `slotKey` 仍兼容 |
| 8 | 锁行 `slotKey` | 新任务恒 null（`slot_key` 列留空），历史任务保留 |
| 9 | 重发 / 补发 | 沿用原任务的目标槽位，按同一前缀规则展开 |

**DDL（已执行）**

```sql
ALTER TABLE iot_intimg_push_task
    ADD COLUMN target_slots TEXT NULL COMMENT '运营勾选的目标槽位 JSON' AFTER versions_json;
```

**注意**

- 设备仍是**按需下载**：推送只保证清单下发，不代表所有槽位立刻生效。
- bin 生成完全在服务端（`BoltStarBinConverter` + 内置图渲染），前端只上传 PNG；
  联调后若 bin 观感有问题，只改渲染侧，不动接口与前端。
